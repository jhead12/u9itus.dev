## 1. Data Integrity System

### What was built
A central enforcement layer that ensures politician records never contain garbage data (AI/scraper artifacts).

**Files:**
| File | Purpose |
|---|---|
| `app/Support/PoliticianDataRules.php` | Central rules class — all whitelists, validators, normalizers |
| `app/Console/Commands/AuditPoliticianDataIntegrity.php` | Artisan command to scan/fix/deactivate bad rows |
| `app/Models/Politician.php` | `saving` hook that normalizes party/state and blocks artifact names on every write |
| `database/migrations/2026_07_06_150001_add_politician_data_check_constraints.php` | MySQL CHECK constraints mirroring the rules (guarded, non-fatal) |
| `.github/workflows/sync-candidates.yml` | Runs audit step after sync |
| `.github/workflows/refresh-map-candidates.yml` | Runs audit step after refresh |

**Rules enforced:**
- `full_name` — rejects AI artifact phrases (e.g. "No candidates", "TBD", "Election"), word count > 6, length > 120
- `party_affiliation` — normalized to canonical list: Democratic, Republican, Independent, Libertarian, Green, Nonpartisan, No Party Preference
- `state` — must be valid 2-letter USPS code or full state name (resolved to code)
- `term_status` — must be one of: seated, active, running, lost, retired, former, eliminated

**Key method added (commit `6f72af72`):**
```php
// PoliticianDataRules::resolveStateAbbreviation()
// Maps 'CALIFORNIA' → 'CA', 'NEW YORK' → 'NY', etc.
// Returns null for unmappable values.
PoliticianDataRules::resolveStateAbbreviation('CALIFORNIA'); // → 'CA'
```

**Production audit command:**
```bash
railway run php artisan politicians:audit-data-integrity --fix --deactivate --limit=10000
```
- `--fix` normalizes party/state/term_status in place
- `--deactivate` hides rows with unfixable artifact names (sets `is_active=false`)
- `--limit` caps rows scanned per run

### What was built

| `resources/views/standalone/admin/user-details.blade.php` | User detail card |
| `resources/views/standalone/admin/kyc.blade.php` | KYC queue user avatar |

**How the accessor works:**
```php
// app/Models/User.php
public function getAvatarUrlAttribute(): string
{
    $hash = hash('sha256', strtolower(trim($this->attributes['email'] ?? '')));
    $name = urlencode($this->attributes['name'] ?? $this->attributes['first_name'] ?? 'User');
    return "https://www.gravatar.com/avatar/{$hash}?s=128&d=initials&name={$name}&r=g";
}
```

- `d=initials` — Gravatar generates a colored letter-circle when no photo is set (matches existing UI style)
- `r=g` — G-rated only
- Once a user creates a Gravatar at gravatar.com with their registered email, their real photo appears automatically — no app changes needed

**API key stored in:**
- `.env`: `AVATAR_API_KEY=...`
- `config/services.php`: `config('services.gravatar.api_key')`
- The key is wired for future Phase 2 (profile enrichment on signup) but not yet used for display

**Future Phase 2 (not yet implemented):** On registration, call `GET https://api.gravatar.com/v3/profiles/{sha256_hash}` with Bearer token to pre-fill `first_name`, `last_name`, `location`, `verified_accounts`.

## 6. Architecture Notes

- **No DB migrations** needed for Gravatar — pure accessor pattern
- **Data rules are layered**: app-level (model hook) → command-level (audit) → DB-level (CHECK constraints)
- **`saveQuietly()`** is used in the audit command to bypass model events when fixing rows (prevents the saving hook from rejecting unfixable values during cleanup)
- **`AVATAR_API_KEY` format**: `9723:gk-...` — this is the Gravatar Bearer token format for the REST API v3
